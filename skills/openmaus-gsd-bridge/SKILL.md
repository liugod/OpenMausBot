# OpenMausBot / GSD bridge

Use when the user asks to use GSD for a coding project. This is a local development workflow, not a background scheduler. Follow the user's requested scope and preserve existing projects, bot configurations and data.

1. Determine the exact absolute Git repository root and the intended task from the user or reliable current project context. Never substitute a guessed repository. Do not ask to repeat information already available; if the target remains unclear, ask which repository to use.
2. Choose a stable unique task ID (ASCII letters, numbers, hyphens or underscores), record it for retries, and run the installed bridge script:

   `node "{{OMB_GSD_BRIDGE}}" prepare --repository "<absolute Git root>" --task "<task-id>"`

   When constructing a PowerShell command, use literal single-quoted arguments and double any embedded apostrophe; do not interpolate project names or paths as executable code. It refuses dirty source checkouts and prepares a detached worktree at the current committed HEAD with GSD v1.21.0. A retry with the same ID returns the existing record. Treat `needs_inspection` or any error as a stop: report the actual reason rather than deleting files or silently inventing another task ID.
3. Create the linked OpenMaus goal immediately after preparation, using the exact task ID, a short task title and the user's full request:

   `node --experimental-strip-types "{{OMB_GSD_GOAL}}" --task "<task-id>" --title "<title>" --request "<request>"`

   If the user explicitly identifies an existing OpenMaus goal, instead run `node --experimental-strip-types "{{OMB_GSD_GOAL}}" --task "<task-id>" --goal "<goal-id>"`; never guess which existing goal to modify. Use safe literal arguments as above. The stable task ID makes retries idempotent. If linking fails, report the error and do not claim the phases are syncing. The goal is a progress record and does not itself start a second execution.
4. Call `list_bots` and select a suitable existing coding bot. Use `coordinate_bots` with `thread="new"` for this task, and assign it the exact task ID, returned `worktree`, `baseCommit`, the user's full request, limits, and acceptance criteria. Include the exact standalone marker `[[OMB-GSD:<task-id>]]` in the assignment text, substituting the real task ID. Tell it to use its `openmaus-gsd-worker` skill, execute in that worktree and read the installed `.codex/skills/gsd-onboard/SKILL.md` for an existing project or the specific requested GSD workflow. Tell it not to work in the source checkout, not to overwrite existing planning state, and to report actual files, test results and Git status. Preserve the user's approval and budget limits; never assume GSD may publish, merge, message outsiders or change permissions. After receiving the actual coordinate receipt, verify its exact `requestId` using `node --experimental-strip-types "{{OMB_GSD_CONTROL}}" register --task "<task-id>" --assignment "<requestId>"`. Do this before ending the turn; if registration fails, tell the user control is unavailable and do not guess a worker thread.
5. An assignment receipt means dispatched, not completed. End your turn and wait for the actual worker result using the host's normal coordination mechanism. Do not start a second copy while the first is in progress. If the runtime cannot load or execute the GSD workflow, or asks for user input, report that state and stop rather than claiming success.
6. On return, use `node "{{OMB_GSD_BRIDGE}}" status --task "<task-id>"` to read the current worktree HEAD, tracked-change indicator and GSD phase snapshot. This is a status projection, not independent proof of correctness. Check actual files, tests and Git results before reporting completion. If the worktree is detached, report that; do not claim a branch, commit or push unless it actually exists.

The GSD planner/executor agent roles are distinct from OpenMaus bots; do not claim typed GSD multi-agent dispatch, automatic execution limits, persistent recovery, or a verified final result without evidence. The host periodically projects GSD roadmap phases into the linked goal; it does not convert phase completion into goal acceptance or start GSD itself.

## Change, pause and resume

For a later user request, identify the existing task from this conversation and run `node --experimental-strip-types "{{OMB_GSD_CONTROL}}" status --task "<task-id>"`. Never guess between tasks or use a different worker thread. Choose a new stable ASCII command ID, save it for retries, then run `node --experimental-strip-types "{{OMB_GSD_CONTROL}}" request --task "<task-id>" --command "<command-id>" --kind "<pause|change|resume>" --request "<the user's actual instruction>"`. Use safe literal arguments. Duplicate command IDs with different requests are refused. A change or resume cannot be dispatched while the registered work is active; if the user wants a change during work, record the change, request a separate pause, and dispatch the change only once the pause has been confirmed. When the pause returns, inspect the queued change and continue it without asking the user to repeat the request. If the worker has already finished normally before the pause was dispatched, cancel the undispatched pause and continue with the pending change. Do not claim the request has been applied merely because it was recorded.

Before dispatching a change after pausing, inspect the current GSD planning and compare it with the user's request. If the baseline changed during the pause, record your explicit review with `node --experimental-strip-types "{{OMB_GSD_CONTROL}}" rebase-change --task "<task-id>" --command "<command-id>" --note "<what changed and why this baseline is appropriate>"`. Never blindly rebase a conflicting change.

Run `node --experimental-strip-types "{{OMB_GSD_CONTROL}}" reserve --task "<task-id>" --command "<command-id>"`. If it reports conflict or another action in flight, inspect and report it; rebase only after checking the actual intervening changes. Send the returned request to the returned bot **in the returned existing thread** using `coordinate_bots`, including both exact `marker` and `taskMarker`, the returned baseline hashes and worktree, the full user instruction, and the action. Tell the worker to use `openmaus-gsd-worker` and return real evidence. For pause, ask it to follow GSD pause-work and stop at a safe point; for resume, ask it to read GSD resume-work; for a change, ask it to update GSD planning only after confirming the returned baseline still matches. Preserve all user permissions and scope. Record the actual receipt immediately: `node --experimental-strip-types "{{OMB_GSD_CONTROL}}" attach --task "<task-id>" --command "<command-id>" --assignment "<requestId>"`. Then end the turn and wait for the real worker result. Do not send a second copy if the result or receipt is uncertain.

When the worker returns, run `node --experimental-strip-types "{{OMB_GSD_CONTROL}}" reconcile --task "<task-id>" --command "<command-id>"`. If it says uncertain, inspect the real assignment and files; do not label a pause or change successful without the required evidence. A verified pause confirms the registered worker and GSD handoff only, not external async jobs. For a change whose planning files changed, inspect the actual roadmap and requirements against the user's instruction; only then record the review with `node --experimental-strip-types "{{OMB_GSD_CONTROL}}" confirm-change --task "<task-id>" --command "<command-id>" --note "<specific verification>"`. If the process stopped after reserving but before saving a receipt, reconcile to look for the exact marker; do not resend when the outcome is unknown. `cancel` is only for an undispatched pending or conflicting command. After manually checking the exact thread and files, `dismiss --task <task-id> --command <command-id> --note <review>` can close an uncertain command only when the recorded worker completed normally and no matching command assignment is active; it does not say the command succeeded.

Resume checks that the recorded handoff has not changed and that its `async_jobs` list contains no active or unknown jobs. If it cannot establish that, stop and investigate those jobs; do not assume they stopped. If the handoff later changes after the jobs are actually resolved, inspect the new handoff and job evidence, then explicitly record the review with `review-handoff --task <task-id> --command <pause-command-id> --note <specific-evidence>` before resuming. This checks listed jobs only; it does not prove the absence of unlisted external work.
